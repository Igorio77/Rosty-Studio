# Rostify — план дальнейшей разработки

*На основе анализа README.md, бизнес-плана (Rostify_Plan_RU.docx) и текущего прототипа интерфейса (RostaStudioSchedule.jsx). Август 2026.*

## 1. Текущее состояние проекта

Проверил все три файла. Вывод: **готов только фронтенд-прототип интерфейса**, без какого-либо сохранения данных и без бэкенда. Ниже — честная инвентаризация.

### Что уже реально работает (в браузерном прототипе, на моковых данных в памяти)

- Экран расписания: виды Год / Месяц / Неделя / День / Custom-период с переключением и навигацией по датам.
- Дневной редактор: сетка "позиции × время" с шагом времени (5–60 мин), назначение смен, полосы-Гант прямо в дневном виде, комментарии к шаблону.
- Шаблоны смен: создание, редактирование, удаление, привязка к отделу и цвету.
- Недельный вид: drag-and-drop назначений, выбор замены из списка, кнопка "Rotate All".
- Команда (Team): таблица сотрудников, добавление/редактирование/архивирование/удаление (в памяти).
- Настройки: отделы, роли, шаг времени, светлая/тёмная тема, цветовая палитра.
- Навигация, боковое меню, переключатель workspace/роли пользователя (пока декоративный).

### Что оформлено как заглушка (пункт меню есть, экран — "Coming soon")

Print Center, Dashboard (KPI), Report Center, Off Tracker, Notifications, About, Help.

### Чего нет вообще

- **Сохранения данных.** Всё живёт в `useState` — обновление страницы стирает все изменения. Нет ни RxDB, ни IndexedDB, ни localStorage.
- **Бэкенда.** Нет PostgreSQL, нет API, нет сервера вообще.
- **Авторизации.** Кнопка "Log in / switch account" — это просто текст без логики.
- **Импорта Excel/CSV.**
- **Синхронизации и многопользовательского режима.**
- **Упаковки в десктоп-приложение (Capacitor).**
- **Интеграций с внешними системами.**
- **Безопасности** (шифрование, RBAC, журнал изменений) — в плане это отмечено как открытый вопрос.

Другими словами: сделан насыщенный, кликабельный UI-макет ядра продукта (Фаза 0 из README почти закрыта на уровне дизайна), но ни одной строчки инфраструктуры для реального использования командой ещё нет.

## 2. Главный вывод

Планы (README и docx) написаны заранее и остаются актуальными по архитектуре — их не нужно переписывать. Но их фазы описывают идеальный порядок "с нуля", а по факту Фаза 0 по UI уже почти пройдена, а вот backend/local-first часть Фазы 0 — нет. План ниже — это не замена README, а конкретизация: что делать в следующие недели, опираясь на то, что уже построено.

## 3. Пошаговый план

### Шаг 1 — Зафиксировать прототип как контракт данных (1 неделя)
Прежде чем писать backend, нужно формально описать структуры, которые уже неявно существуют в JSX (`STAFF`, `TEMPLATES`, `assignments`, `roster`). Задача: превратить их в TypeScript-типы / JSON Schema, которые станут основой и для PostgreSQL-схемы, и для RxDB-коллекций. Это самый дешёвый шаг, который снимает риск рассинхронизации фронтенда и бэкенда позже.

### Шаг 2 — Ввести локальное хранилище (RxDB/IndexedDB) (1–2 недели)
Заменить `useState` на RxDB-коллекции (People, Templates, ScheduleEntries) по типам из шага 1. Цель: приложение переживает перезагрузку страницы без сервера. Это самая рискованная и самая ценная часть local-first архитектуры — её нужно доказать раньше бэкенда.

### Шаг 3 — Backend: PostgreSQL + JSONB + REST API (2–3 недели)
Поднять PostgreSQL-схему (People/Templates/ScheduleEntries) с партиционированием по дате и составными индексами `(date, employee)` и `(date, position)`, как описано в README. Реализовать минимальный REST API (CRUD + ревизии для конфликтов). Пока без прод-синхронизации — просто рабочий сервер для следующего шага.

### Шаг 4 — Фоновая синхронизация RxDB ↔ сервер (1–2 недели)
Подключить replication-протокол RxDB к API из шага 3. Критерий готовности: два браузера/устройства с одним аккаунтом видят одни и те же данные с задержкой в фоне, и приложение продолжает работать офлайн.

### Шаг 5 — Экран входа и роли (1 неделя)
Добавить настоящий логин (email/пароль или magic link) и связать его с существующим переключателем ролей (License Keeper/Admin/Manager/...), чтобы права редактирования реально ограничивались, а не были декоративными.

### Шаг 6 — Импорт команды из Excel/CSV (3–5 дней)
Реализовать то, что заявлено в README и бизнес-плане: шаблон для выгрузки, парсинг, валидация, запись в People. Технически несложно и сильно снижает порог входа для реального клиента с большой командой.

### Шаг 7 — Закрыть заглушки, важные для первого клиента
Приоритет — не по алфавиту, а по тому, что нужно, чтобы "продукт заменил Excel" (критерий выхода Фазы 1 из README):
1. **Dashboard/KPI** — хотя бы базовые метрики (людей на смене, покрытие) поверх реальных данных из шага 3.
2. **Print Center** — печать расписания важна для операций с бумажными подиум-листами (упомянуто в бизнес-плане).
3. **Report Center**, **Off Tracker**, **Notifications** — можно отложить в Фазу 4/бэклог, как и в README.

### Шаг 8 — Пилот на реальной операции
И README, и бизнес-план сходятся в одном: лучший следующий шаг после рабочего ядра — не больше фич, а реальное использование на настоящей казино-операции с партнёром по дизайну. Рекомендую зафиксировать это как явный milestone после шага 6, а не после всех фич.

### Шаг 9 — Capacitor / десктоп-сборка (1 неделя, можно параллельно с шагом 7)
Технически независим от остального — можно собрать простой `.exe` сразу после того, как в шаге 2 появится работающее локальное хранилище, не дожидаясь синхронизации.

### Шаг 10 — Безопасность и интеграции (после пилота)
Шифрование, журнал изменений расписаний (почти бесплатно благодаря интервальной модели), затем API/CSV-интеграции с внешними операционными системами — по запросу первых клиентов, как и рекомендует бизнес-план.

## 4. Ориентировочная последовательность по времени

| Этап | Шаги | Срок |
|---|---|---|
| Данные и локальное хранилище | 1–2 | 2–3 недели |
| Backend и синхронизация | 3–4 | 3–5 недель |
| Доступ и импорт | 5–6 | 1.5–2 недели |
| Готово к пилоту | 7 (KPI + Print) | 1–2 недели |
| **Пилот на реальной операции** | 8 | — |
| Десктоп-сборка | 9 | 1 неделя (параллельно) |
| Безопасность и интеграции | 10 | после пилота, по фидбэку |

**Итого до пилота: ориентировочно 8–12 недель** при команде из 1 фронтенд- и 1 бэкенд-разработчика — это совпадает с составом команды, рекомендованным в README.

## 5. Ближайший конкретный шаг

Начать с Шага 1: выписать типы данных из существующего JSX-кода (`STAFF`, `TEMPLATES`, `assignments`, `roster`, структуры смен) в отдельный файл схемы. Это займёт 1–2 дня, ничего не сломает в текущем прототипе и станет фундаментом для шагов 2 и 3.
